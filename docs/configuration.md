# Справочник конфигурации

Единственный файл настроек — `config.cfg` (INI-формат, UTF-8) в корне
проекта. Здесь расписана каждая секция и опция: дефолт — это значение из
кода (`dedup/settings.py`), которое применится, если опцию не указать. Оно
может отличаться от того, что стоит в твоём живом `config.cfg`.

## Как это работает

- Файл читается один раз на старте (`load_config()`), результат — неизменяемый
  набор дата-классов `Settings`. Изменение `config.cfg` под работающим
  скриптом ничего не меняет.
- Переменные окружения из `.env` **приоритетнее** секции `[pyrogram]`:
  `TG_API_ID` перекрывает `api_id`, `TG_API_HASH` — `api_hash`.
- Все найденные проблемы собираются в **один** `ConfigError` со списком —
  скрипт выходит с кодом 2, не начав работу. Какие-то проверки мягче:
  некорректные значения в `[ignore_list]`/`[ignore_regex]` попадают в тот же
  список, а вот недоступный юзернейм в ignore-списках останавливает прогон
  уже после старта (см. ниже).
- Отдельные значения мягко клампятся, а не ругаются: `sleep_threshold` ≥ 1,
  `batch_delete_size` 1..100, `lzma_preset` 0..9,
  `dynamic_space_coefficient` ≥ 1.1, `archive_mode`/`matching_mode` при
  опечатке откатываются к `forward`/`sort` соответственно.

## `[core]` — главное поведение

| Опция | Дефолт | Описание |
|---|---|---|
| `chat_list` | *(пусто)* | Чаты обработки через запятую: числовые ID, `@username`, ссылки `t.me` (включая приватные `+hash`). Пустой список = нечего обрабатывать |
| `dry_run` | `True` | Режим симуляции: полный прогон с печатью плана в лог, но без изменений в Telegram. БД синхронизируется по-настоящему |
| `report_only` | `False` | Только отчёты о дубликатах (как команда `report`): без удаления и без верификации через API |
| `revoke_private_chats` | `True` | Удаление в личных чатах/обычных группах: `True` — у всех участников, `False` — только у себя. Супергруппы/каналы всегда «у всех» |
| `keep_priority` | *(пусто)* | Каскад выбора оригинала — см. ниже |
| `keep_newest_duplicate` | `False` | **Устарело.** Используется только при пустом `keep_priority`: `True` → оригинал = самое новое сообщение, `False` → самое старое |

### `keep_priority` — кого оставить

В группе дубликатов одна запись становится оригиналом, остальные — кандидаты
на удаление. Критерии перечисляются через запятую; следующий применяется,
когда предыдущий дал ничью:

```ini
keep_priority = largest ~ 3%, best_meta, oldest
```

| Критерий | Смысл | Допуск `~N%` |
|---|---|---|
| `oldest` / `newest` | по `message_id` (меньше = старее) | запрещён |
| `largest` / `smallest` | по размеру файла | можно |
| `longest` / `shortest` | по длительности | можно |
| `best_meta` | у кого заполнены и валидны performer и title (0–2 балла; `<unknown>` и title, совпадающий с именем файла, не считаются) | запрещён |
| `longest_clean_name` | самое длинное имя после очистки от мусора | можно |

Правила:

- Допуск `~N%` расширяет ничью: `largest ~ 3%` — все в пределах 3% от
  максимума считаются равными и идут дальше по каскаду. Знак `%` необязателен,
  диапазон 0–100.
- Если ни `oldest`, ни `newest` не указаны — `oldest` добавляется в конец
  автоматически (гарантия единственного победителя).
- `oldest` и `newest` вместе — ошибка конфигурации. Повтор критерия — тоже.
- Пустое значение → срабатывает устаревший `keep_newest_duplicate`.

## `[ignore_list]` и `[ignore_regex]` — защита от удаления

```ini
[ignore_list]
-1001986217699 = 4973, 4660, 3621

[ignore_regex]
* =
    (?i)\blive\b
    ^Мой сет
-1001986217699 =
    (?i)Король
```

- `ignore_list`: `chat_id = message_id, message_id, ...` — конкретные
  сообщения, которые никогда не удаляются. Ключом может быть и `@username` —
  резолвится на старте; если резолв не удался, прогон останавливается
  (лучше не начать, чем удалить незащищённое).
- `ignore_regex`: одна регулярка на строку (продолжения — с отступом).
  Матчится `re.search` по `file_name`, `performer` и `title` **из локальной
  БД**. Регистр чувствителен — добавляй `(?i)` при необходимости. Ключ `*` —
  паттерны для всех чатов.
- Защита применяется в последний момент: сообщения остаются в чате, но и в
  группе дубликатов продолжают участвовать (оригиналом может стать другое
  сообщение).

## `[pyrogram]` — клиент Telegram

| Опция | Дефолт | Описание |
|---|---|---|
| `api_id`, `api_hash` | *(пусто)* | Креды с my.telegram.org. Лучше держать в `.env` (`TG_API_ID`/`TG_API_HASH` приоритетнее) |
| `session_name` | `my_account` | База имени файла сессии (`my_account.session`, `my_account.lock`) |
| `proxy_url` | *(пусто)* | Прокси: `socks5://user:pass@host:port`, `http://...` или MTProto-ссылка `t.me/proxy?...` — её скрипт сам превращает в локальный SOCKS5-мост |
| `sleep_threshold` | `300` | Сколько секунд клиент ждёт FloodWait автоматически, дольше — исключение |

## `[archive]` — архивация перед удалением

| Опция | Дефолт | Описание |
|---|---|---|
| `archive_before_delete` | `False` | Пересылать дубликаты в запасной чат перед удалением |
| `archive_target` | `me` | Куда: `me`/`self` — Избранное, `@username`, числовой ID |
| `archive_mode` | `forward` | `forward` — пересылка батчами до 100, сохраняет «переслано из…»; `copy` — чистые новые сообщения, по одному, медленнее |
| `archive_hide_sender` | `False` | Прятать автора пересылки (только для `forward`; в `copy` автора и так нет) |
| `abort_delete_on_archive_failure` | `True` | `True` — батч, который не удалось заархивировать целиком, не удаляется; `False` — удалять всё равно (опасно) |

Важно:

- **Не указывай в `archive_target` чат из `chat_list`** — на следующем
  прогоне скрипт задедуплит собственный архив (скрипт предупредит в логе).
- Ни forward, ни copy не обходят защищённый контент
  (`has_protected_content`) — такие батчи не будут удалены.
- Перед прогоном цель проверяется: для канала нужны права на постинг. Если
  цель недоступна, а `dry_run = False` — остановка на старте.
- При архивации в начало пишется текстовый разделитель: из какого чата,
  сколько файлов, когда.

## `[fuzzy_matching]` — нечёткий поиск

Полное описание алгоритма — [fuzzy.md](fuzzy.md). Краткая сводка:

| Опция | Дефолт | Описание |
|---|---|---|
| `enable` | `False` | Включить fuzzy-поиск. `False` — только точные совпадения (UID/метаданные) |
| `matching_mode` | `set` | `sort` — строгий (лишние слова снижают балл), `set` — агрессивный (лишние слова игнорируются; хорош для каверов и замусоренных имён) |
| `threshold` | `0.90` | Порог итогового сходства, 0..1. Не находит дубли — снижай до 0.85 |
| `max_duration_diff_sec` | `3` | Жёсткий пре-фильтр: пары с большей разницей длительности не сравниваются вовсе |
| `name_power` | `1.0` | Степень текстового сходства; >1 — строже (давит частичные совпадения), <1 — мягче. Обязателен > 0 |
| `duration_power` | `3.0` | Степень сходства длительности |
| `size_power` | `1.0` | Степень сходства размера |
| `weight_name` | `0.50` | Вес имени в итоговом score |
| `weight_duration` | `0.30` | Вес длительности |
| `weight_size` | `0.20` | Вес размера |
| `penalty_numbers_mismatch` | `0.08` | Штраф при несовпадении множеств чисел в названиях («op 1» vs «op 2», BWV 813 vs 814) |
| `use_jaccard_penalty` | `False` | `False` — бинарный штраф; `True` — пропорционально мере Жаккара (общие числа уменьшают штраф) |
| `use_meta_fuzzy` | `True` | Сравнивать и теги performer+title с именем во всех комбинациях (имя-имя, имя-мета, мета-имя, мета-мета), берётся лучший результат. Спасает файлы вроде `audio_123.mp3` с нормальными тегами |

Ограничения-на-ошибку: сумма весов должна быть 1.0 (±0.01);
`max_duration_diff_sec` ≥ 0; `name_power` > 0; `duration_power` и `size_power`
≥ 0.

### Математика степеней

Числовые критерии считаются как отношение `(меньшее / большее)`, возведённое
в степень `power`:

| Степень | Эффект | Когда использовать |
|---|---|---|
| `p = 1.0` | линейно: разница в 2 раза = 50% баллов | нейтральный вариант |
| `p > 1.0` | строго: кривая вглубь, мелкие отличия жестко штрафуются | поиск абсолютных клонов |
| `p < 1.0` | лояльно: корень, огромные отличия прощаются | одна песня в разных форматах |
| `p = 0` | критерий всегда даёт 1.0, т.е. выключен | игнорировать критерий |
| `p < 0` | запрещено — ломает алгоритм | — |

Текстовый критерий устроен так же, только вместо отношения — сырой score
RapidFuzz (0..1). Пример: `score=1.0` не меняется при любой степени, а
частичное совпадение 0.87 при `name_power=1.5` превратится в 0.82.

### Пресеты из практики

| Цель | Настройки |
|---|---|
| Только клоны, максимальная строгость | `matching_mode = sort`, `duration_power = 84`, `max_duration_diff_sec = 2` |
| Золотая середина для музыки | `matching_mode = set`, `threshold = 0.90`, `duration_power = 3.0–4.0`, `name_power = 1.3–1.6` |
| Различать битрейты (320 vs 128) | `size_power = 5.0` |
| Склеивать FLAC и MP3 одной песни | `size_power = 0.2` |
| Ремиксы/радио-версии одной дорожки | `duration_power = 0.5` + сильно поднятый `max_duration_diff_sec` |

| Опция | Дефолт |

## `[system_safety]` — блокировка и диск

| Опция | Дефолт | Описание |
|---|---|---|
| `lock_timeout` | `0` | Ожидание lock-файла, сек: `0` — сразу выйти, `-1` — ждать вечно, `>0` — ждать столько (можно дробное) |
| `min_free_space_mb` | `0.0` | `>0` — простая проверка «свободно не меньше N МБ»; `0.0` — динамический расчёт |
| `dynamic_space_coefficient` | `1.5` | Множитель оценки: 1.5 = место под бэкап (100%) + 50% запаса |
| `dynamic_space_safety_buffer_mb` | `16.0` | Фиксированный запас поверх динамической оценки |

Динамическая оценка исходит из текущего размера БД (включая `-wal`/`-shm`) и
каталога бэкапов — её цель, чтобы прогон не упал посреди работы без места.

## `[performance]` — батчи и БД

| Опция | Дефолт | Описание |
|---|---|---|
| `sync_batch_size` | `7000` | Раз в сколько сообщений коммитить при синхронизации |
| `batch_delete_size` | `100` | Сообщений в батче удаления из Telegram (лимит API — 100, значение клампится в 1..100) |
| `verify_chunk_size` | `200` | Сообщений в одном запросе верификации (Telegram рекомендует ≤200) |
| `verify_concurrency` | `4` | Параллельных запросов верификации/резолва |
| `db_cache_size` | `-256000` | PRAGMA `cache_size`; отрицательное — в КиБ (~256 МБ) |

Эти значения влияют на скорость и нагрузку на аккаунт, но не на результат.
Если ловишь FloodWait — снижай `verify_concurrency`.

## `[backup]` — бэкапы БД

| Опция | Дефолт | Описание |
|---|---|---|
| `backup_on_startup` | `True` | Делать бэкап при запуске (кроме `repair` и `export`) |
| `backup_only_if_changed` | `True` | Пропускать бэкап, если хэш содержимого БД не изменился |
| `rotate_before_backup` | `False` | `False` — сначала новый бэкап, потом ротация (безопаснее); `True` — наоборот (экономит место) |
| `max_backups` | `1` | Лимит «горячих» `.bak`: лишние удаляются или сжимаются. `0` — новые бэкапы сразу уходят в архив |
| `archive_old_backups` | `True` | Сжимать вытесняемые бэкапы в `.xz` вместо удаления |
| `lzma_preset` | `7` | Уровень сжатия 0–9 (0–3 быстро, 7–9 медленно и плотно) |
| `max_archives` | `4` | Лимит `.bak.xz` в `backup/`, старейшие удаляются |

Команда `repair` бэкап на старте не создаёт (чтобы не копать уже
копанную яму), остальные режимы — согласно настройкам.

## Рецепты

**«Пропускает дубликаты»** → снизь `threshold` до 0.85–0.87; проверь по
`export cleaned-names`, не режет ли очистка имён важные части; попробуй
`matching_mode = set`, если стоит `sort`.

**«Склеивает разное»** → подними `name_power` (1.3–1.6 давит частичные
совпадения 0.83–0.90); включи бинарный штраф (`use_jaccard_penalty = False`)
и/или подними `penalty_numbers_mismatch` до 0.10–0.12; снизь
`max_duration_diff_sec`.

**«Боится удалить лишнее»** → `dry_run` + `report_only` до полной уверенности,
`ignore_regex` на особо ценные названия, архивация включена,
`abort_delete_on_archive_failure = True` (дефолт).

**«Медленно синхронизирует»** → обычно упирается в Telegram, а не в скрипт;
подними `sleep_threshold`, снизь число чатов в `chat_list` за прогон.

**«Файл сессии/БД переехали»** → поменяй `session_name` / `[paths]`; БД можно
просто перенести и указать новый `db_file`.
