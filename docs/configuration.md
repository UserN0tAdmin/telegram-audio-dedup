# Справочник конфигурации

Единственный файл настроек — `config.cfg` (INI-формат, UTF-8) в корне
проекта. Стартовая точка — приложенный шаблон: `cp config.example.cfg
config.cfg` (полностью прокомментирован) — дальше правь под себя. Здесь
расписана каждая секция и опция: дефолт — это значение из
кода (`dedup/settings.py`), которое применится, если опцию не указать. Оно
может отличаться от того, что стоит в твоём живом `config.cfg`.

## Как это работает

- Файл читается один раз на старте (`load_config()`), результат — неизменяемый
  набор дата-классов `Settings`. Изменение `config.cfg` под работающим
  скриптом ничего не меняет.
- Переменные окружения из `.env` **приоритетнее** секции `[pyrogram]`:
  `TG_API_ID` перекрывает `api_id`, `TG_API_HASH` — `api_hash`.
- Аргументы командной строки приоритетнее всего: **CLI > `.env` > `config.cfg`**
  (см. [раздел ниже](#перекрытие-аргументами-командной-строки)).
- Все найденные проблемы собираются в **один** `ConfigError` со списком —
  скрипт выходит с кодом 2, не начав работу. Какие-то проверки мягче:
  некорректные значения в `[ignore_list]`/`[ignore_regex]` попадают в тот же
  список, а вот недоступный юзернейм в ignore-списках останавливает прогон
  уже после старта (см. ниже).
- Отдельные значения мягко клампятся, а не ругаются: `sleep_threshold` ≥ 1,
  `batch_delete_size` 1..100, `lzma_preset` 0..9,
  `dynamic_space_coefficient` ≥ 1.1, `archive_mode`/`matching_mode` при
  опечатке откатываются к `forward`/`sort` соответственно.

## Перекрытие аргументами командной строки

Любую опцию можно перекрыть на один запуск, не трогая `config.cfg`. Флаги
глобальные: работают с любой подкомандой и в полном прогоне, указываются
до или после подкоманды (позднее указание приоритетнее).

| Флаг | Эквивалент `--set` | Смысл |
|---|---|---|
| `--set SECTION.OPTION=VALUE` | — | Любая опция из справочника ниже; повторяемый |
| `--dry-run` / `--no-dry-run` | `--set core.dry_run=true/false` | Симуляция только на этот запуск |
| `--chat A,B` | `--set core.chat_list=A,B` | Чаты прогона (замещает `chat_list`) |
| `--threshold F` | `--set fuzzy_matching.threshold=F` | Порог fuzzy 0..1 |

Правила:

- значение пишется как в `config.cfg`: `true/false`, числа, списки через
  запятую; рез по первому `=`, поэтому `=` внутри значения допустим;
- при конфликте `--set` приоритетнее сахарных флагов; несколько `--set` на
  один ключ — побеждает последний;
- ключи `[ignore_list]`/`[ignore_regex]` свободные (ID чата или `*`):
  `--set ignore_list.-1001986217699=4973,4660`; многострочные значения
  `[ignore_regex]` из CLI задать нельзя — только однострочный паттерн;
- неизвестная секция/опция — выход с кодом 2 со списком допустимых ключей;
  остальная валидация и клампинг — те же, что для файла;
- каждое применённое перекрытие печатается в лог со старым значением:
  `CLI-перекрытие: core.dry_run = true (в конфиге: false)`.

Примеры:

```bash
python main.py --dry-run --chat @music_shiz                    # симуляция по одному чату
python main.py --no-dry-run --chat -1001986217699         # бой по одному чату
python main.py --set fuzzy_matching.enable=true report    # fuzzy на один report
python main.py search "запрос" --set logging.log_level_console=DEBUG
python main.py --threshold 0.85 --set core.report_only=true
python main.py --set paths.exports_dir=/tmp/exp export filenames 123
```

## `[core]` — главное поведение

| Опция | Дефолт | Описание                                                                                                                               |
|---|---|----------------------------------------------------------------------------------------------------------------------------------------|
| `chat_list` | *(пусто)* | Чаты обработки через запятую: числовые ID, `@username`, ссылки `t.me` (включая приватные `+hash`). Пустой список = нечего обрабатывать |
| `dry_run` | `True` | Режим симуляции: полный прогон с печатью плана в лог, но без изменений в Telegram или БД.          |
| `report_only` | `False` | Только отчёты о дубликатах (как команда `report`): без удаления и без верификации через API                                            |
| `revoke_private_chats` | `True` | Удаление в личных чатах/обычных группах: `True` — у всех участников, `False` — только у себя. Супергруппы/каналы всегда «у всех»       |
| `keep_priority` | *(пусто)* | Каскад выбора оригинала — см. ниже                                                                                                     |
| `keep_newest_duplicate` | `False` | **Устарело.** Используется только при пустом `keep_priority`: `True` → оригинал = самое новое сообщение, `False` → самое старое        |

### `keep_priority` — кого оставить

Каскад выстраивает записи группы дубликатов в очередь на сохранение:
первый, прошедший проверку через API, становится оригиналом, остальные —
кандидаты на удаление. Критерии перечисляются через запятую; каждый
следующий сужает круг «равных», оставшихся после предыдущего:

```ini
keep_priority = largest ~ 2%, best_meta, oldest
```

| Критерий | Сравнивает | Допуск `~N%` |
|---|---|--------------|
| `oldest` / `newest` | `message_id` (меньше = раньше опубликовано) | запрещён     |
| `largest` / `smallest` | размер файла | разрешён     |
| `longest` / `shortest` | длительность | разрешён        |
| `best_meta` | качество тегов, 0–2 балла (см. ниже) | запрещён     |
| `longest_clean_name` | длину имени файла после очистки от мусора | разрешён        |

Как работает один уровень каскада:

- **Нет значения — выбываешь.** Запись, у которой значения критерия нет
  (нулевая длительность, пустое очищенное имя), проигрывает уровень, если
  хоть у одного конкурента значение есть.
- **Нет значения ни у кого — уровень пропускается** целиком, состав
  кандидатов не меняется.
- **Допуск расширяет ничью.** `largest ~ 3%` при лучшем размере 10,4 МБ
  даёт порог ≈ 10,09 МБ: все, кто не меньше, проходят дальше. Знак `%`
  необязателен, диапазон 0–100.
- Гарантия финала: если не указан ни `oldest`, ни `newest`, в конец
  автоматически добавляется `oldest` — `message_id` уникальны, поэтому
  каскад всегда заканчивается единственным победителем.
- `oldest` и `newest` вместе — ошибка конфигурации. Повтор критерия —
  тоже. Пустое значение → срабатывает устаревший `keep_newest_duplicate`.

#### Пример: каскад в действии

Группа из четырёх дублей одного трека, каскад `largest ~ 3%, best_meta,
oldest` (третий добавлен автоматически — можно не писать):

| Файл | Размер | Теги | `message_id` |
|---|---|---|---|
| A | 10,2 МБ | исполнитель + название | 120 |
| B | 10,4 МБ | только название | 200 |
| C | 8,1 МБ | нет | 95 |
| D | 10,3 МБ | нет | 310 |

```text
A, B, C, D ──largest ~3%──> A, B, D ──best_meta──> A ──(oldest)──> оригинал A
```

1. `largest ~ 3%`: лучший — B (10,4 МБ), порог ≈ 10,09 МБ; остаются
   A, B, D, выбывает C.
2. `best_meta` (допуска нет): у A — 2 балла, у B — 1, у D — 0. Остаётся
   только A.
3. `oldest`: кандидат один — победитель найден.

Итоговая очередь сохранения: **A → B → D → C** — каскад строит её целиком,
а не только победителя. Если A не пройдёт проверку через API (удалён из
чата или изменён), оригиналом станет B, а удалены будут только D и C:
очередь страхует от потери лучшей копии из-за устаревшей БД.

#### Баллы `best_meta`

| Балл | За что |
|---|---|
| +1 | валидный `performer` — не пустой и не плейсхолдер вида `<unknown>` |
| +1 | валидный `title`, отличающийся от имени файла: совпадающее с именем файла название — мусор сайтов-качалок и не засчитывается |

## `[ignore_list]` и `[ignore_regex]` — защита от удаления

Две независимые страховки от удаления нужного: `[ignore_list]` — точечно,
по номерам сообщений; `[ignore_regex]` — по содержимому (имя файла и теги).
Обе секции необязательны: нет секции — нет защиты.

```ini
[ignore_list]
-1001986217699 = 4973, 4660, 3621

[ignore_regex]
* =
    (?i)\blive\b
    ^Мой сет
-1001986217699 =
    (?i)Король
```

### Ключи — идентификатор чата

| Ключ | Как обрабатывается |
|---|---|
| Числовой ID | `-1001986217699` — супергруппа/канал, `123456789` — личный чат/обычная группа. Берётся как есть, **без проверки через API**: опечатка в цифре старт не сломает, но защита молча не сработает |
| `@username` | Резолвится в числовой ID на старте (конкурентные запросы, как у `chat_list`; лимит — `verify_concurrency`). Недоступный чат — критическая ошибка, прогон останавливается до любых удалений: лучше не начать, чем удалить незащищённое |
| `*` | Только в `[ignore_regex]`: паттерны для всех чатов сразу, складываются с паттернами конкретного чата. В `[ignore_list]` `*` не поддерживается — строка уйдёт в резолв как «юзернейм» и остановит прогон с ошибкой |

### `[ignore_list]` — точечная защита

- Формат значения: `message_id, message_id, ...` — номер сообщения в этом
  чате (последнее число в ссылке вида `t.me/…/4660`). Пробелы вокруг
  запятых не важны, пустые элементы пропускаются.
- Ожидаются только целые числа: любое не-число — ошибка конфигурации,
  старт не состоится.
- Несколько ключей, резолвящихся в один чат (например, ID и `@username`),
  объединяются.

### `[ignore_regex]` — защита по содержимому

- Одна регулярка на строку; продолжения — с отступом (стандартный
  многострочный INI). Каждая строка обрезается по пробелам, пустые
  пропускаются.
- Синтаксис Python `re`, сопоставление — `re.search`: ищется вхождение, а
  не вся строка (`^Мой сет` — «начинается с», `^Мой сет$` — точное
  совпадение).
- Матчится по `file_name`, `performer` и `title` **из локальной БД**;
  достаточно совпадения в любом из полей. Сообщение должно быть в базе —
  свежие попадают туда при синхронизации в начале того же прогона.
- Регистр чувствителен — добавляй `(?i)` при необходимости.
- Некомпилируемый паттерн — ошибка конфигурации с указанием строки и
  причины от `re`; старт не состоится.

### Когда срабатывает

Разбор — на старте вместе с остальным конфигом: любые ошибки обеих секций
попадают в общий `ConfigError` (выход с кодом 2). Применение — в самый
последний момент, уже после выбора оригиналов, прямо перед архивацией и
удалением. Отсюда следствия:

- Защищённое сообщение остаётся в группе дубликатов и участвует в выборе
  оригинала наравне с остальными — `keep_priority` про защиту не знает.
  Если оригиналом стал защищённый, остальные участники группы всё равно
  удалятся: защита лишь вычёркивает сообщение из списка на удаление.
- В `dry_run` фильтр тоже применяется: напечатанный план уже без
  защищённых сообщений — по нему удобно проверять, что защита работает.
- Защищённые кандидаты не архивируются: `[archive]` получает уже
  отфильтрованный список.
- Записи, которых уже нет в Telegram, всё равно чистятся из БД — беречь
  там нечего.
- `report`/`report_only` ничего не удаляют, на содержимое отчёта списки
  не влияют, но `@username`-ключи резолвятся и там: недоступный чат
  остановит прогон.

Сработавшую защиту видно в логе:

```text
Пропускаю удаление 2 сообщений из чата … (в списке игнорирования).
Regex-защита: сообщение 4660 ('Король и Шут') совпало с '(?i)Король'.
Пропускаю удаление 1 сообщений из чата … (regex-защита).
```

Перекрытие из CLI — см. [раздел выше](#перекрытие-аргументами-командной-строки):
`--set ignore_list.<чат>=…` замещает список этого чата из `config.cfg`
целиком, а `[ignore_regex]` из CLI задаётся только однострочным паттерном.

## `[pyrogram]` — клиент Telegram

| Опция | Дефолт | Описание |
|---|---|---|
| `api_id`, `api_hash` | *(пусто)* | Креды с my.telegram.org. Лучше держать в `.env` (`TG_API_ID`/`TG_API_HASH` приоритетнее) |
| `session_name` | `my_account` | База имени файла сессии (`my_account.session`, `my_account.lock`) |
| `proxy_url` | *(пусто)* | Прокси: `socks5://user:pass@host:port`, `http://...` или MTProto-ссылка `t.me/proxy?...` — мост требует `pip install -e .[mtproxy]`, без него ссылка идёт как есть |
| `sleep_threshold` | `300` | Сколько секунд клиент ждёт FloodWait автоматически, дольше — исключение |

## `[archive]` — архивация перед удалением

| Опция | Дефолт | Описание |
|---|---|---|
| `archive_before_delete` | `False` | Пересылать дубликаты в запасной чат перед удалением |
| `archive_target` | `me` | Куда: `me`/`self` — Избранное, `@username`, числовой ID |
| `archive_mode` | `forward` | `forward` — пересылка батчами до 100, сохраняет «переслано из…»; `copy` — чистые новые сообщения, по одному, медленнее |
| `archive_hide_sender` | `False` | Прятать автора пересылки (только для `forward`; в `copy` автора и так нет) |
| `archive_send_header` | `True` | Текстовый разделитель «Удалено из чата …» перед батчами; `False` — не засорять архив служебными сообщениями |
| `abort_delete_on_archive_failure` | `True` | `True` — батч, который не удалось заархивировать целиком, не удаляется; `False` — удалять всё равно (опасно) |

Важно:

- **Не указывай в `archive_target` чат из `chat_list`** — на следующем
  прогоне скрипт задедуплит собственный архив (скрипт предупредит в логе).
- Ни forward, ни copy не обходят защищённый контент
  (`has_protected_content`) — такие батчи не будут удалены.
- Перед прогоном цель проверяется: для канала нужны права на постинг. Если
  цель недоступна, а `dry_run = False` — остановка на старте.
- При архивации в начало пишется текстовый разделитель: из какого чата,
  сколько файлов, когда.

## `[fuzzy_matching]` — нечёткий поиск

Полное описание алгоритма — [fuzzy.md](fuzzy.md). Краткая сводка:

| Опция | Дефолт  | Описание                                                                                                                                                                                    |
|---|---------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `enable` | `False` | Включить fuzzy-поиск. `False` — только точные совпадения (UID/метаданные)                                                                                                                   |
| `matching_mode` | `set`   | `sort` — строгий (лишние слова снижают балл), `set` — агрессивный (лишние слова игнорируются; хорош для каверов и замусоренных имён)                                                        |
| `threshold` | `0.90`  | Порог итогового сходства, 0..1. Не находит дубли — снижай до 0.85                                                                                                                           |
| `max_duration_diff_sec` | `3`     | Жёсткий пре-фильтр: пары с большей разницей длительности не сравниваются вовсе<br/> Окно по длительности, т.е. в каком промежутке будут сравниваться файлы                                  |
| `name_power` | `1.5`   | Степень текстового сходства; >1 — строже (давит частичные совпадения), <1 — мягче. Обязателен > 0                                                                                           |
| `duration_power` | `4.0`   | Степень сходства длительности                                                                                                                                                               |
| `size_power` | `0.9`   | Степень сходства размера                                                                                                                                                                    |
| `weight_name` | `0.50`  | Вес имени в итоговом score                                                                                                                                                                  |
| `weight_duration` | `0.30`  | Вес длительности                                                                                                                                                                            |
| `weight_size` | `0.20`  | Вес размера                                                                                                                                                                                 |
| `penalty_numbers_mismatch` | `0.08`  | Штраф при несовпадении множеств чисел в названиях («op 1» vs «op 2», BWV 813 vs 814)                                                                                                        |
| `use_jaccard_penalty` | `False` | `False` — бинарный штраф; `True` — пропорционально мере Жаккара (общие числа уменьшают штраф)                                                                                               |
| `use_meta_fuzzy` | `True`  | Сравнивать и теги performer+title с именем во всех комбинациях (имя-имя, имя-мета, мета-имя, мета-мета), берётся лучший результат. Спасает файлы вроде `audio_123.mp3` с нормальными тегами |

Ограничения-на-ошибку: сумма весов должна быть 1.0 (±0.01);
`max_duration_diff_sec` ≥ 0; `name_power` > 0; `duration_power` и `size_power`
≥ 0.

### Математика степеней

Числовые критерии считаются как отношение `(меньшее / большее)`, возведённое
в степень `power`:

| Степень | Эффект | Когда использовать |
|---|---|---|
| `p = 1.0` | линейно: разница в 2 раза = 50% баллов | нейтральный вариант |
| `p > 1.0` | строго: кривая вглубь, мелкие отличия жестко штрафуются | поиск абсолютных клонов |
| `p < 1.0` | лояльно: корень, огромные отличия прощаются | одна песня в разных форматах |
| `p = 0` | критерий всегда даёт 1.0, т.е. выключен | игнорировать критерий |
| `p < 0` | запрещено — ломает алгоритм | — |

Текстовый критерий устроен так же, только вместо отношения — сырой score
RapidFuzz (0..1). Пример: `score=1.0` не меняется при любой степени, а
частичное совпадение 0.87 при `name_power=1.5` превратится в 0.82.

## `[system_safety]` — блокировка и диск

| Опция | Дефолт | Описание |
|---|--------|---|
| `lock_timeout` | `0`    | Ожидание lock-файла, сек: `0` — сразу выйти, `-1` — ждать вечно, `>0` — ждать столько (можно дробное) |
| `min_free_space_mb` | `0.0`  | `>0` — простая проверка «свободно не меньше N МБ»; `0.0` — динамический расчёт |
| `dynamic_space_coefficient` | `1.5`  | Множитель оценки: 1.5 = место под бэкап (100%) + 50% запаса |
| `dynamic_space_safety_buffer_mb` | `8.0`  | Фиксированный запас поверх динамической оценки |

Динамическая оценка исходит из текущего размера БД (включая `-wal`/`-shm`) и
каталога бэкапов — её цель, чтобы прогон не упал посреди работы без места.

## `[performance]` — батчи и БД

| Опция | Дефолт | Описание |
|---|---|---|
| `sync_batch_size` | `7000` | Раз в сколько сообщений коммитить при синхронизации |
| `batch_delete_size` | `100` | Сообщений в батче удаления из Telegram (лимит API — 100, значение клампится в 1..100) |
| `verify_chunk_size` | `200` | Сообщений в одном запросе верификации (Telegram рекомендует ≤200) |
| `verify_concurrency` | `4` | Параллельных запросов верификации/резолва |
| `db_cache_size` | `-256000` | PRAGMA `cache_size`; отрицательное — в КиБ (~256 МБ) |

Эти значения влияют на скорость и нагрузку на аккаунт, но не на результат.
Если ловишь FloodWait — снижай `verify_concurrency`.

## `[backup]` — бэкапы БД

| Опция | Дефолт | Описание |
|---|---|---|
| `backup_on_startup` | `False` | Делать бэкап при запуске онлайн-команд (полный прогон, `report`, `sync`, `download`); не делается для `repair`, а офлайн-команды (`export`, `search`) до бэкапа просто не доходят |
| `backup_only_if_changed` | `True` | Пропускать бэкап, если хэш содержимого БД не изменился |
| `rotate_before_backup` | `False` | `False` — сначала новый бэкап, потом ротация (безопаснее); `True` — наоборот (экономит место) |
| `max_backups` | `1` | Лимит «горячих» `.bak`: лишние удаляются или сжимаются. `0` — новые бэкапы сразу уходят в архив |
| `archive_old_backups` | `True` | Сжимать вытесняемые бэкапы в `.xz` вместо удаления |
| `lzma_preset` | `7` | Уровень сжатия 0–9 (0–3 быстро, 7–9 медленно и плотно) |
| `max_archives` | `4` | Лимит `.bak.xz` в `backup/`, старейшие удаляются |

Команда `repair` бэкап на старте не создаёт (чтобы не копать уже
копанную яму), остальные режимы — согласно настройкам.

## Рецепты

**«Пропускает дубликаты»** → снизь `threshold` до 0.85–0.87; проверь по
`export cleaned-names`, не режет ли очистка имён важные части; попробуй
`matching_mode = set`, если стоит `sort`.

**«Склеивает разное»** → подними `name_power` (1.3–1.6 давит частичные
совпадения 0.83–0.90); включи бинарный штраф (`use_jaccard_penalty = False`)
и/или подними `penalty_numbers_mismatch` до 0.10–0.12; снизь
`max_duration_diff_sec`.

**«Боится удалить лишнее»** → `dry_run` + `report_only` до полной уверенности,
`ignore_regex` на особо ценные названия, архивация включена,
`abort_delete_on_archive_failure = True` (дефолт).

**«Медленно синхронизирует»** → обычно упирается в Telegram, а не в скрипт;
подними `sleep_threshold`, снизь число чатов в `chat_list` за прогон.

**«Файл сессии/БД переехали»** → поменяй `session_name` / `[paths]`; БД можно
просто перенести и указать новый `db_file`.
