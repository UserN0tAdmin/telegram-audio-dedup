# Использование: команды, пайплайн, безопасность

Про установку и первый вход — [installation.md](installation.md). Здесь
считаем, что `config.cfg` с `chat_list` уже настроен (справочник опций —
[configuration.md](configuration.md)).

## Идентификаторы чатов

Везде, где нужен чат, принимаются три формы:

- числовой ID: `-1001986217699` (супергруппы/каналы), `123456789` (личка);
- `@username`;
- ссылка: `https://t.me/username` или `https://t.me/+invite_hash`.

Нюанс: в `chat_list` и в командах `report`/`sync`/`download` имена и ссылки
резолвятся **онлайн** через API (заодно попадают в кэш сессии). А вот
аргументы `export`-подкоманд резолвятся **офлайн** — чтением файла сессии
`my_account.session`. Если чат с таким `@username` никогда не встречался в
предыдущих прогонах, экспорт по юзернейму не найдёт его — укажи числовой ID
или прогони сначала онлайн-режим.

## Команды

### `python main.py` — полный прогон

Основной режим. Для каждого чата из `chat_list` по очереди:

1. **Проверка прав** — см. [раздел про права](#права-в-чатах).
2. **Синхронизация** — выкачиваются метаданные всех аудио чата в БД
   (фильтры `AUDIO` и `DOCUMENT` с аудио-mime). Повторные прогоны
   инкрементальные: запоминается `newest_scanned_id`, сканируются только
   сообщения новее. Записи вставляются `INSERT OR IGNORE` — синхронизацию
   можно прерывать и перезапускать без дублей.
3. **Отчёт или дедупликация**:
   - если это команда `report` или в конфиге `report_only = True` — строится
     текстовый отчёт, чат пропускается дальше;
   - если чат досинхронизирован до конца прошлым прогоном (флаг
     `is_fully_synced`) — запускается поиск дубликатов; если синхронизация
     прошла только частично (например, прервана), этап очистки пропускается —
     сначала надо досмотреть историю.

Поиск дубликатов внутри чата — четыре шага:

1. **Группировка** по локальной БД: точное совпадение (`file_unique_id` или
   все метаданные разом) или fuzzy-движок (если `fuzzy_matching.enable`).
   Как именно считаются дубликаты — [fuzzy.md](fuzzy.md).
2. **Верификация через API**: все сообщения найденных групп запрашиваются у
   Telegram заново, батчами по `verify_chunk_size`, с ограничением
   параллелизма `verify_concurrency`.
3. **Классификация** каждого сообщения группы по свежим данным API:
   - сообщение исчезло из Telegram или больше не аудио → запись удаляется
     только из БД;
   - контент изменился (другой файл/имя/теги) → запись БД обновляется;
    - всё совпадает и это не первый валидный в группе → кандидат на удаление
      из Telegram. «Первый валидный» определяется каскадом `keep_priority`:
      например, «самый большой (в пределах 2%), при ничьей — с полными тегами,
      при ничьей — самый старый».
4. **Применение**: фильтрация ignore-защиты, затем (если включена)
   архивация батчами и удаление из Telegram; из БД вычищаются только записи,
   реально исчезнувшие из Telegram. Все изменения БД — одной транзакцией в
   конце.

### `python main.py sync [чат] [--force]`

Чисто синхронизация: выкачивает метаданные аудио в БД и
завершается — без отчётов, поиска дубликатов и удаления. Без аргумента
берутся все чаты из `chat_list`, с аргументом — один чат. Удобно, когда
нужен свежий слепок чата для офлайн-команд (`export`, `search`, `download`)
или когда новый чат надо досинхронизировать заранее, не запуская полный цикл.

Флаг `--force` игнорирует сохранённый курсор и сканирует историю целиком:
полезен после ручных правок в Telegram или при подозрении на пропуски.
Существующие записи не трогаются и не задваиваются, курсор по завершении
пересчитывается; при падении посреди прогона старый курсор сохраняется.
Учтите: записи об уже удалённых из Telegram сообщениях при этом **не**
вычищаются — это работа верификации боевого прогона или `repair`.

### `python main.py repair`

Ремонт БД: проверка целостности, поиск битых записей (пустой
`file_unique_id`, отсутствующие метаданные, отрицательные размер/длительность)
со сверкой против Telegram, сброс кривых курсоров синхронизации, перестройка
индексов и `VACUUM`. Полезен после падения посреди прогона или при жалобах
валидации на старте.

### `python main.py download <чат>`

Скачивает все аудио чата из БД в `downloads/<chat_id>/`. Требует, чтобы чат
был синхронизирован (иначе «нет записей — сначала запустите синхронизацию»).
Параллельная загрузка: 3 воркера, с Telegram Premium — 6. Уже скачанные
файлы пропускаются по совпадению размера и даты изменения (прерванная
закачка продолжается с места, без повторной перекачки целых файлов); после
скачивания файлу возвращается оригинальная дата сообщения. Если свободного
места меньше суммарного размера — предупреждение и 10 секунд на Ctrl+C.

### `python main.py export ...`

Пять действий, все работают **офлайн по локальной БД** — без подключения к
Telegram, lock-файла и бэкапа:

| Действие | Файл | Что внутри |
|---|---|---|
| `filenames <чат>` | `exports/<чат>/<ts>_filenames.txt` | Имена файлов по алфавиту |
| `filenames-url <чат>` | `..._filenames_with_urls.txt` | Имя + ссылка `t.me/c/...`, колонки выровнены по визуальной ширине |
| `cleaned-names [чат]` | `..._cleaned_names.csv` | Диагностика очистки имён: исходное → после `clean_filename` → финальная fuzzy-форма |
| `cleaned-meta [чат]` | `..._cleaned_meta.csv` | То же для тегов: performer, title → очищенная строка |
| `xlsx [чат]` | `..._database_export.xlsx` | Все несистемные таблицы БД, по листу на таблицу |

Для `cleaned-names`, `cleaned-meta` и `xlsx` чат можно не указывать — тогда
экспортируется вся БД в `exports/_full/`. CSV пишется в `utf-8-sig` с
разделителем `;` — русский Excel открывает без танцев. `cleaned-*` экспорты —
главный инструмент отладки fuzzy: они показывают ровно ту строку, которую
видит матчер (см. [fuzzy.md](fuzzy.md)). Ссылки `t.me/c/...` в
`filenames-url` валидны для супергрупп и каналов; в личных чатах могут не
открыться (скрипт предупредит об этом в логе).

### `python main.py search "<запрос>"`

Нечёткий поиск с пониманием опечаток по всем аудио во всех чатах БД.
Работает **офлайн по локальной БД** — как экспорты, без подключения к
Telegram, lock-файла и бэкапа. Быстрый способ вспомнить, где лежит трек,
не зная точного имени файла.

- запрос сравнивается и с именем файла, и с тегами (`performer+title`),
  причём в двух вариантах: дедуп-очистка — та же, что у fuzzy-движка (см.
  [fuzzy.md](fuzzy.md)), поэтому рекламные вставки, сайты и суффиксы копий
  не мешают обычным запросам, — и лёгкая нормализация, сохраняющая этот
  «мусор»: по сайтам-качалкам (`zaycev`, `muzlome`), расширениям (`flac`,
  `mp3`) и цифровым ID тоже можно искать; из всех оценок берётся лучшая;
- скорер — всегда `token_set_ratio`, независимо от `matching_mode` в
  конфиге (настройка строгости дедупликации на поиск не влияет): порядок
  слов в запросе не важен, слово-подмножество считается точным попаданием
  (100%);
- флаг `--wratio` переключает на WRatio — выручает, когда ищете короткий
  обрывок с опечаткой по длинным названиям (партиал-совпадения), но шкала
  сжата: слово найдено = 90, перестановка слов = 95;
- вывод — топ-200 совпадений от лучшего к худшему, только результаты со
  схожестью от 50%; колонки выровнены по самой широкой строке результата
  (с учётом кириллицы);
- порог регулируется при запуске: `--min-score N` (целое 0..100) —
  уменьшите, чтобы увидеть больше отдалённых совпадений, увеличьте для
  строгого поиска: `python main.py search "запрос" --min-score 85`;
- лимит выдачи: `--limit N` (целое от 1) — перекрывает топ-200, например:
  `python main.py search "запрос" --limit 50`.

## Типичные сценарии

**Первичная расчистка чата:**

```bash
python main.py report      # синхронизация + отчёты в exports/<chat_id>/
```

Одна команда, ничего не удаляет: чаты синхронизируются (инкрементально),
для каждого складывается наглядный отчёт — группы, метки `[KEEP]`, разбор
связей со score (пример выше). Изучаешь: группы разумные? оригиналы
выбираются так, как хочется? Если fuzzy что-то не то — тюнишь
`[fuzzy_matching]` и повторяешь `report`.

Вариант «подольше не доверять скрипту» — `report_only = True` в `[core]`:
тогда каждый обычный прогон останавливается на отчётах, без отдельной
команды.

**Боевой прогон:**

```ini
[core]
dry_run = False

[archive]
archive_before_delete = True
archive_target = me
```

```bash
python main.py            # архивация в Избранное + удаление
```

Если хочется финальной перестраховки — оставь `dry_run = True` и прогони
без `report_only`: в логе напечатается план удаления **после** верификации
через API. Это менее наглядно, чем отчёт (план в логе, без имён и ссылок),
зато показывает ровно то, что будет исполнено.

Разовые вариации без правки `config.cfg` — флагами перекрытия
(`--no-dry-run`, `--chat`, `--set SECTION.OPTION=VALUE`; справочник —
[configuration.md → Перекрытие аргументами](configuration.md#перекрытие-аргументами-командной-строки)):

```bash
python main.py --no-dry-run --chat @music_shiz    # бой только по @music_shiz
```

**Регулярное обслуживание** — теми же командами: инкрементальная
синхронизация подхватит только новые сообщения, дедуп пройдёт по свежим
данным, бэкап БД создастся на старте (если изменилась).

## Права в чатах

- **Личные чаты** — обрабатываются всегда.
- **Read-only режимы** (`report`, `sync`, `download`, а также
  `dry_run`/`report_only` в конфиге) — достаточно быть участником чата;
  не-участнику разрешено, если чат публичный.
- **Боевой режим** — нужно быть владельцем чата или админом с правом удаления
  сообщений (`can_delete_messages`). Иначе чат пропускается с ошибкой в лог.

Удаление в личных чатах и обычных группах управляется `revoke_private_chats`:
`True` — «удалить у всех» (дефолт), `False` — «удалить только у себя». В
супергруппах и каналах сообщения всегда удаляются для всех — так устроен
Telegram.

## Модель безопасности

Скрипт удаляет сообщения в чужих чатах, поэтому предохранителей много.
Нулевой и главный — рабочий процесс: сначала `report` и разбор групп,
потом бой. Дальше — технические предохранители, по порядку срабатывания:

1. **Один экземпляр** — lock-файл `<session_name>.lock`; вторая копия сразу
   выходит (или ждёт `lock_timeout`).
2. **Свободное место** — перед прогоном проверка: статическая (МБ) или
   динамическая (оценка от размера БД и бэкапов).
3. **Бэкап БД на старте** — если включён (`backup_on_startup`), создаётся до
   любых изменений; повторные бэкапы при неизменной БД пропускаются по хэшу,
   старые ротируются/сжимаются.
4. **Валидация БД** — повреждённая база останавливает прогон до работы с
   Telegram (лечится `repair`).
5. **Верификация через API** — удаление планируется только по сообщениям,
   подтверждённым живым запросом к Telegram. Любая ошибка API хотя бы по
   одному сообщению группы — **вся группа пропускается** (fail-safe).
6. **Игнор-листы** — `ignore_list` (конкретные `message_id` чата) и
   `ignore_regex` (защита по имени файла/тегам) отсекают кандидатов в
   последний момент, уже после классификации.
7. **Архивация перед удалением** — если включена: сначала forward/copy в
   архивный чат, потом удаление. Батч удаляется только если заархивирован
   **целиком** (при `abort_delete_on_archive_failure = True`); недоархивированный
   батч остаётся в чате до следующего прогона. Если архивная цель недоступна,
   а `dry_run = False` — прогон останавливается ещё на старте, чтобы не
   удалять без страховки. Защищённый контент (`has_protected_content`) не
   пересылается и не копируется — такой батч просто не будет удалён.
8. **`dry_run`** — если всё же добрались до удаления, а он включён: в лог
   печатается полный план (что удалено из TG, что из БД, что обновлено), и
   ничего не выполняется.
9. **Честность БД** — из БД записи удаляются только для сообщений,
   подтверждённо исчезнувших из Telegram (если Telegram удалил 97 из 100 в
   батче, в БД вычистятся ровно 97).

Важная деталь: `dry_run` защищает только этап применения — синхронизация БД
и в нём выполняется по-настоящему (это безопасно, БД — локальная).

## Куда что пишется

| Действие | Путь |
|---|---|
| Отчёт о дубликатах | `exports/<chat_id>/<таймстемп>_report_duplicates.txt` |
| Экспорты чата | `exports/<chat_id>/<таймстемп>_<вид>.<ext>` |
| Экспорт всей БД | `exports/_full/<таймстемп>_<вид>_of_music_library.<ext>` |
| Скачанные аудио | `downloads/<chat_id>/` |
| Бэкапы БД | `backup/<имя_БД>_<дата>.sqlite.bak` (`.bak.xz` — сжатые) |
| Лог | `log/script_activity.log` (+ ротированные `.1`…`.5`) |

Таймстемп одного прогона общий для всех чатов — файлы отчётов легко
собираются в снапшот запуска. В консоль лог пишется с уровнем
`log_level_console` (обычно INFO), в файл — `log_level_file` (обычно DEBUG,
включая детальные `[MATCH]`-строки fuzzy-матчера).
