# Установка и первый запуск

## Требования

- **Python 3.12+** (используются PEP 695-типы и `itertools.batched`).
- Аккаунт Telegram, из которого есть доступ к нужным чатам. Скрипт работает
  через MTProto как **личный аккаунт** (Kurigram — форк pyrogram), не как бот.
- Креды приложения с <https://my.telegram.org>: `api_id` и `api_hash`.

## Установка

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

`pyproject.toml` — канонический манифест зависимостей; `requirements.txt` — те
же пакеты с точными пинами для воспроизводимости. Для разработки — 
`pip install -r requirements-dev.txt` (pytest, ruff, mypy и т.п., см.
[tests/README.md](../tests/README.md)).

На Linux/macOS ставится `uvloop`, на Windows — `winloop`: скрипт подхватывает
их автоматически для ускорения asyncio; если не установлены — работает и на
стандартном цикле (с предупреждением в логе).

## Файлы конфигурации

Нужны два файла в корне проекта (оба в `.gitignore`, secrets не утекут):

### `.env` — креды приложения

```ini
TG_API_ID=123456
TG_API_HASH=0123456789abcdef0123456789abcdef
```

Переменные из `.env` **приоритетнее** значений `api_id`/`api_hash` в
`config.cfg`. Если не задано ни там, ни там — при старте будет предупреждение,
а клиент Telegram не сможет зайти. Трижды подумай, прежде чем вставлять креды
от основного клиента куда-то ещё — скрипт с ними делает всё то же, что и ты.

### `config.cfg` — основная конфигурация

Без него скрипт откажется стартовать (`ОШИБКА КОНФИГУРАЦИИ: Файл 'config.cfg'
не найден`, код выхода 2). Минимум для старта:

```ini
[core]
chat_list = -1001234567890, @some_music_chat

[fuzzy_matching]
enable = True
```

Все остальные опции имеют дефолты — полный справочник со значениями по
умолчанию и рекомендациями: [configuration.md](configuration.md). Живой пример
с подробными комментариями каждого параметра — в самом `config.cfg`.

Ошибка в конфиге не уронит прогон молча: все найденные проблемы (например,
сумма весов fuzzy не равна 1.0, кривой regex, неизвестный критерий
`keep_priority`) собираются в один `ConfigError` и печатаются списком.

## Первый вход

При первом запуске `python main.py` клиент попросит авторизоваться: телефон,
код из Telegram, при необходимости пароль двухфакторки. После этого в корне
появится файл сессии:

```
my_account.session   # SQLite-сессия авторизации (не коммитить!)
my_account.lock      # lock-файл одного экземпляра, живёт во время прогона
```

Имя файла задаётся `session_name` в секции `[pyrogram]`. Файл сессии = полный
доступ к аккаунту: логика работы с ним — только чтение (скрипт открывает его
в read-only для офлайн-резолва имён чатов), но береги его как пароль.
Вдобавок скрипт выставляет `umask 077`, так что новые файлы (сессия, логи,
lock) создаются доступными только владельцу.

Первый прогон удобнее всего делать сразу с отчётом: `python main.py report` —
скрипт синхронизирует чаты, соберёт БД и сложит наглядные отчёты о дубликатах
в `exports/`, не трогая ничего в Telegram. Дефолтный `dry_run = True`
остаётся фоновым предохранителем на случай боевых прогонов. Дальше —
[usage.md](usage.md).

## Прокси

Задаётся одной строкой `proxy_url` в секции `[pyrogram]`. Поддерживаются два
вида:

**Обычный URL** — socks5 или http, логин/пароль опциональны:

```ini
proxy_url = socks5://user:pass@127.0.0.1:1080
proxy_url = http://127.0.0.1:8080
```

**MTProto-ссылка** (те самые `https://t.me/proxy?server=...&secret=...`):
скрипт сам поднимает локальный SOCKS5-мост (пакет `mtproxy-bridge`) и
переключает транспорт на padded-вариант, если этого требует секрет. Ничего
дополнительно настраивать не надо — просто вставь ссылку:

```ini
proxy_url = https://t.me/proxy?server=example.com&port=443&secret=ee...
```

Если мост не поднялся (кривая ссылка, сеть), прогон остановится с критической
ошибкой до подключения к Telegram. Локальные прокси тестировались; про
удалённые — проверяй сам.

## Что появится после первого прогона

| Путь | Что это |
|---|---|
| `music_library.sqlite` | Основная БД (WAL-режим; рядом бывают `-wal`/`-shm` файлы) |
| `my_account.session` | Сессия Telegram |
| `my_account.lock` | Lock-файл одного экземпляра (только на время прогона) |
| `backup/` | Бэкапы БД: `<имя_БД>_<дата>.sqlite.bak` и сжатые `.bak.xz`, служебный `.latest_backup.hash` |
| `downloads/<chat_id>/` | Скачанные аудио (команда `download`) |
| `exports/<chat_id>/` | Отчёты и экспорты конкретного чата |
| `exports/_full/` | Экспорты всей БД (когда чат не указан) |
| `log/script_activity.log` | Лог с ротацией (`script_activity.log.1`, `.2`, ...) |

Все пути переназначаются в секции `[paths]`. Бэкапы, экспорты и логи растут
медленно, а вот `downloads/` может занять место, сопоставимое с размером
аудиотеки чата — за этим следит проверка свободного места перед прогоном
(`[system_safety]`).

## Частые проблемы

- **«Файл 'config.cfg' не найден»** — конфиг не создан или запущено не из
  корня проекта. Скрипт ищет `config.cfg` в текущем каталоге.
- **`AlreadyRunningError` при старте** — вторая копия скрипта. Управляется
  `lock_timeout` в `[system_safety]`: `0` — сразу выйти, `-1` — ждать вечно.
- **FloodWait** — Telegram ограничивает частоту запросов для активных
  аккаунтов. Порог автоожидания задаёт `sleep_threshold` в `[pyrogram]`
  (дефолт 300 с); всё, что дольше, падает исключением. Лечится паузой и
  меньшим числом чатов за раз.
- **`sqlite3.OperationalError: database is locked`** — БД открыта посторонним
  процессом (например, просмотрщиком SQLite). Закрой его и повтори.
