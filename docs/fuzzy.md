Дубликаты ищутся внутри одного чата, независимо от других чатов. Формально
картина такая: записи чата — вершины графа, «это дубликат» — ребро; группой
считается любая связная компонента размера ≥ 2 (поэтому A~B, B~C собирает
в одну группу все три записи, даже если A и C напрямую не сравнивались).
Вся математика ниже — про то, как проводятся рёбра.

## Общая картина: конвейер

Путь от живого чата до списка на удаление выглядит так:

```
 Telegram API
     │  синхронизация: выкачиваются метаданные всех аудио чата (sync.py)
     ▼
 БД, таблица audios
     (message_id, file_unique_id, file_name, file_size,
      duration, performer, title)
     │
     ▼
 [1] UID-предпроход ......... одинаковый file_unique_id → рёбра «uid»
     │
     ▼
 [2] сортировка по длительности + скользящее окно ±Δt
     │
     ▼
 [3] векторные вклады длительности/размера + динамические пороги
     │
     ▼
 [4] оптимистичный отсев .... даже теоретический максимум текста
     │                        не дотягивает до порога → текст не считается
     ▼
 [5] RapidFuzz (cdist) ...... текстовые скоры пачкой;
     │                        при use_meta_fuzzy — 4 комбинации «имя/мета»
     ▼
 [6] Stage 1 → Stage 2 ...... быстрый отбор без штрафа, затем честный
     │                        штраф и выбор источника текста
     ▼
 [7] граф → BFS ............. связные компоненты ≥ 2 = группы дубликатов
     │
     ▼
 [8] верификация через API .. fail-safe: любая ошибка — группа пропущена
     │
     ▼
 [9] keep_priority .......... кто [KEEP], кто кандидат на удаление; отчёт
```

Шаги [1]–[7] описаны в этом документе; [8]–[9] — в разделе
[«Что происходит с группой дальше»](#что-происходит-с-группой-дальше).

Включается fuzzy секцией `enable = True` в `[fuzzy_matching]` (по умолчанию
выключен — тогда работает только точный режим, см. следующий раздел).
Попробовать на один прогон без правки конфига:

```bash
python main.py --set fuzzy_matching.enable=true report
```

## Откуда берутся данные

Дедупликатор ничего не скачивает: при синхронизации (`sync.py`) из каждого
сообщения чата извлекаются только метаданные аудио и складываются в таблицу
`audios`. Извлекает их `get_audio_attributes()` (`tg.py`): у сообщения
берётся объект `message.audio` (аудио, отправленное как аудио), а если его
нет — `message.document` с mime-типом `audio/*` (аудио, отправленное файлом).

| Поле в БД | Что это | Источник в API |
|---|---|---|
| `message_id` | ID сообщения в чате, ключ записи | `message.id` |
| `file_unique_id` | «отпечаток» файла на серверах Telegram | `.file_unique_id` |
| `file_name` | имя файла | `.file_name` |
| `file_size` | размер в байтах | `.file_size` |
| `duration` | длительность в секундах | `.duration` |
| `performer` | исполнитель из тегов | `.performer` |
| `title` | название из тегов | `.title` |

Любое из этих полей, кроме `chat_id`/`message_id`, может оказаться пустым
(NULL): Telegram отдаёт то, что знал на момент отправки.

**`file_unique_id`** — идентификатор содержимого файла, который Telegram
выдаёт одинаковым байтам. Переслали сообщение — UID тот же; перекачали
тот же файл и загрузили заново — тот же. Разные битрейты, обрезки, версии —
уже разные UID. Это единственный «бесплатный» и гарантированный признак
дубликата, поэтому он используется до всякой нечёткости.

**Мета (`performer` + `title`)** — это теги аудиофайла. Когда файл
загружают в Telegram, сервер сам читает встроенные теги (ID3 у MP3,
Vorbis-комментарии у FLAC/OGG) и отдаёт их в атрибутах сообщения; их же
может задать отправитель. К нам мета попадает уже готовой через API —
никакие теги мы не парсим. Отсюда её особенности:

- аудио, отправленное **файлом** (`document` с mime `audio/*`), тегов не
  имеет вовсе: `performer = title = NULL`;
- отправитель мог залить файл с пустыми или кривыми тегами;
- встречаются плейсхолдеры вроде `<unknown>` — такие поля целиком
  отбрасываются как отсутствующие (`clean_meta`);
- если после отбрасывания ничего не осталось, мета считается пустой и в
  мета-комбинациях сравнения не участвует (см. [Мета-источники](#мета-источники-четыре-комбинации)).

Имя файла и мета — два независимых текстовых описания одного и того же
трека, нередко одно из них мусорное (`audio_123.mp3` с идеальными тегами
или `Queen - Bohemian Rhapsody.mp3` вообще без тегов). Поэтому при
`use_meta_fuzzy = True` они сравниваются во всех комбинациях.

## Этап 0: точные совпадения

Два типа связей ставятся без всякой нечёткости:

- **одинаковый `file_unique_id`** — буквально один и тот же файл на серверах
  Telegram. Гарантированное совпадение; работает в обоих режимах (и в
  точном, и внутри fuzzy как UID-предпроход);
- **полное совпадение метаданных**: `file_name` + `performer` + `title` +
  `file_size` + `duration` равны целиком — путь точного режима
  (`enable = False`).

Нюансы точного сравнения:

- поля сравниваются как кортеж целиком, и NULL считается значением: два
  файла без имени, но с одинаковыми остальными полями — «совпадение»;
- при `enable = True` отдельного этапа «полное совпадение метаданных» нет —
  но такие пары и так набирают порог fuzzy (очевидно: очищенные имена
  идентичны, длительность и размер совпадают), так что ничего не теряется.

Оба типа связей транзитивны и бесплатны — для них не вызывается ни один
текстовый компаратор.

## Конвейер очистки имён

Fuzzy сравнивает не сырые имена, а очищенные — иначе «Track_Name
[myzuka.com].mp3» и «(myzuka.com) track name.mp3» не встретились бы.
Очистка (`clean_filename`) делает следующее по порядку:

1. срезаются медиа-расширения (`.mp3`, `.flac`, …);
2. всё в нижний регистр;
3. убираются суффиксы копий «(1)», «[2]» в конце;
4. имя вида `12345_1737839201` (мусорный ID целиком) проходит как есть,
   минуя остальную очистку;
5. срезается числовой префикс из 5–7 цифр;
6. вырезаются рекламные вставки в скобках с доменом внутри
   (`[myzuka.com]`, `(zaycev.net)`), префиксы `www.`/`http(s)://`,
   «сайтовые» префиксы/суффиксы известных музыкальных помоек
   (muzlome, myzuka, zaycev, zvuk, hitmo, …) и вообще любые токены,
   похожие на домен (`something.ru`);
7. `_` и `-` заменяются пробелами, пробелы схлопываются;
8. в конце удаляются длинные цифровые ID (7+ цифр), которые сайты-качалки
   лепят к имени.

Если после очистки не осталось ничего — берётся имя без расширения как
есть. Примеры (полный список даёт `export cleaned-names`, см.
[Инструменты диагностики](#инструменты-диагностики)):

| Исходное имя | После очистки | Что сработало |
|---|---|---|
| `Track_Name [myzuka.com].mp3` | `track name` | реклама в скобках |
| `zaycev_Artist - Song.mp3` | `artist song` | сайтовый префикс |
| `Artist - Song_1737839201.mp3` | `artist song` | мусорный ID в хвосте |
| `Artist - Song (1).flac` | `artist song` | суффикс копии |
| `12345_1737839201.mp3` | `12345 1737839201` | мусорный ID целиком — проходит как есть |
| `05 - Artist - Song.mp3` | `05 artist song` | короткий номер (1–4 цифры) не срезается |

Теги обрабатываются той же трубой (`clean_meta`): складываются
`performer + title`, плейсхолдеры `<unknown>` выбрасываются, дальше — тот
же `clean_filename`. После очистки идёт финальная нормализация RapidFuzz
(`default_process`: нижний регистр, без пунктуации) — именно эту строку
видит матчер.

Числа для [числового штрафа](#числовой-штраф) извлекаются из очищенного
имени и, отдельно, из очищенной меты: `bwv 813, 5 menuet, 6` →
множество $\{813, 5, 6\}$.

## Формула сходства

### Обозначения

Для пары записей $a, b$ из одного чата:

| Символ | Что это | Опция |
|---|---|---|
| $r_{\text{text}} \in [0,1]$ | текстовое сходство очищенных строк (RapidFuzz, см. ниже) | `matching_mode` |
| $r_{\text{dur}}, r_{\text{size}} \in (0,1]$ | отношения длительности и размера | — |
| $w_n, w_d, w_s$ | веса критериев, в сумме 1 | `weight_name`, `weight_duration`, `weight_size` |
| $p_n, p_d, p_s$ | степени критериев | `name_power`, `duration_power`, `size_power` |
| $\theta$ | базовый порог | `threshold` |
| $\delta$ | числовой штраф | `penalty_numbers_mismatch` |

Отношения считаются симметрично, «меньшее к большему» — запись в 180 с
против 182 с и 182 с против 180 с дают одно и то же:

$$r_{\text{dur}} = \frac{\min(d_a, d_b)}{\max(d_a, d_b)}, \qquad r_{\text{size}} = \frac{\min(s_a, s_b)}{\max(s_a, s_b)}$$

### Итоговый score

$$\mathrm{score}(a, b) \;=\; w_n \cdot r_{\text{text}}^{\,p_n} \;+\; w_d \cdot r_{\text{dur}}^{\,p_d} \;+\; w_s \cdot r_{\text{size}}^{\,p_s} \;-\; \mathrm{pen}(a, b)$$

Словами: у score есть бюджет 1.0, который делится между тремя критериями
по весам (дефолт: имя 0.5, длительность 0.3, размер 0.2). Каждый критерий
отдаёт в общий котёл свою долю, умноженную на своё сходство (возведённое
в степень). Из суммы вычитается штраф за несовпадение чисел в названиях —
он может обнулить до $\delta$ набранных баллов. Пара объявляется
дубликатом, если

$$\mathrm{score}(a, b) \;\ge\; \theta'$$

где $\theta'$ — динамический порог, который умеет снижаться, если у пары
недоступен какой-то критерий.

### Динамический порог: если критерий недоступен

Длительность или размер могут быть неизвестны (NULL или 0 в БД). Такое
поле не должно топить заведомый дубликат — но и «дарить» баллы оно не
должно тоже. Правило простое:

> **нет критерия → его вклад равен 0, а порог снижается на $\theta \cdot w$
> (вес этого критерия, взятый от порога).**

$$\theta' = \theta - \theta \cdot \bigl(w_d \cdot [\text{длит. неизвестна}] + w_s \cdot [\text{размер неизвестен}]\bigr)$$

При дефолтах $\theta = 0.90$, $w_d = 0.3$, $w_s = 0.2$:

| Доступно для сравнения | Порог $\theta'$ | Бюджет критериев |
|---|---|---|
| имя + длительность + размер | 0.90 | 1.00 |
| имя + размер (длительности нет) | $0.90 - 0.27 = 0.63$ | 0.70 |
| имя + длительность (размера нет) | $0.90 - 0.18 = 0.72$ | 0.80 |
| только имя | $0.90 - 0.45 = 0.45$ | 0.50 |

Порог и бюджет снижаются согласованно, поэтому «заведомый дубликат без
длительности» проходит: например, при совпадении имени (1.0) и размера
(0.96) паре без длительности достаточно $0.5 \cdot 1 + 0.2 \cdot 0.96 = 0.69 \ge 0.63$.

Важно: текстовый критерий недоступным не бывает — пустое имя тоже строка,
она просто сравнивается и набирает мало баллов. Снизить порог может только
отсутствие длительности или размера.

### Степени: что делает $(\min/\max)^p$

Отношение $r \in (0,1]$ возводится в степень $p$, и это деформирует шкалу
оценок:

| $p$ | Эффект | Смысл |
|---|---|---|
| $= 1$ | линейно — разница вдвое даёт $0.5$ | нейтрально |
| $> 1$ | строго — кривая вглубь, мелкие отличия жёстко штрафуются | только клоны |
| $< 1$ | лояльно — корень, огромные отличия прощаются | одна песня в разных форматах |
| $= 0$ | критерий выключен ($r^0 = 1$ всегда) | игнорировать критерий |

$p < 0$ запрещено — конфиг это отвергнет. Численно:

| $r = \min/\max$ | $p{=}0$ | $p{=}0.5$ | $p{=}1$ | $p{=}2$ | $p{=}3$ | $p{=}4$ | $p{=}84$ |
|---|---|---|---|---|---|---|---|
| 0.99 (лишняя секунда) | 1 | 0.995 | 0.990 | 0.980 | 0.970 | 0.961 | **0.43** |
| 0.95 (тишина в конце) | 1 | 0.975 | 0.950 | 0.903 | 0.857 | 0.814 | **0.01** |
| 0.90 | 1 | 0.949 | 0.900 | 0.810 | 0.729 | 0.656 | ~0 |
| 0.50 (вдвое длиннее) | 1 | 0.707 | 0.500 | 0.250 | 0.125 | 0.063 | ~0 |
| 0.10 (FLAC vs MP3) | 1 | 0.316 | 0.100 | 0.010 | 0.001 | ~0 | ~0 |

Интуиция: у степени $p > 1$ кривая прижимается к нулю всюду, кроме
окрестности $r = 1$. Отсюда смысл пресетов:

- `duration_power = 84` — «клоны и только клоны»: даже 1% разницы
  длительности ($r = 0.99$) оставляет критерию $0.99^{84} = 0.43$ балла
  из 1, а 5% — почти ноль. Любая обрезка или другой рип проваливают порог;
- `size_power = 0.2` — наоборот, «размер не важен»: разница размеров в
  10 раз даёт $0.1^{0.2} = 0.63$ — критерий теряет лишь треть балла.
  Так склеиваются FLAC и MP3 одной песни.

Текстовая степень $p_n$ работает точно так же, только по $r_{\text{text}}$:
частичное совпадение $0.87$ при $p_n = 1.5$ превращается в $0.81$, и
пограничные «похожие, но разные» треки проваливают порог. Для $p_n$
запрещено даже $0$ (иначе текст всегда давал бы максимум), требуется
строго $> 0$.

### Числовой штраф

Два трека с почти одинаковыми именами, но разными номерами («op 1» vs
«op 2», «BWV 813» vs «BWV 814», «Part 1» vs «Part 2») — это *разные*
треки, а текстовое сходство у них высокое. Штраф ловит именно это: из
очищенного имени (и отдельно из меты) вытаскиваются все числа во
множество — `bwv 813, 5 menuet, 6` → $\{813, 5, 6\}$ — и множества
сравниваются.

Если множества равны (в том числе оба пусты) — штрафа нет. Иначе:

$$
\mathrm{pen}(a, b) = \begin{cases}
\delta \cdot \left(1 - \dfrac{|N(a) \cap N(b)|}{|N(a) \cup N(b)|}\right), & \text{режим Жаккара} \\[8pt]
\delta, & \text{бинарный режим}
\end{cases}
$$

- **бинарный** (`use_jaccard_penalty = False`, дефолт): любое несовпадение
  множеств — полный штраф $\delta$. Просто и предсказуемо: «BWV 813» не
  склеится с «BWV 814»;
- **Жаккар** (`use_jaccard_penalty = True`): штраф пропорционален доле
  *различающихся* чисел. Пересечение делим на объединение — это мера
  Жаккара; единица минус неё — расстояние Жаккара. Много общих чисел →
  маленький штраф. Прощает совпадающие номера движений (у сюиты Баха
  части 5 и 6 общие), но заодно легче склеивает и соседние сюиты.

Максимум штрафа в обоих режимах одинаковый — $\delta$; регулируется
опцией `penalty_numbers_mismatch` (дефолт 0.08).

### Текстовое сходство: режимы `sort` и `set`

Оба — меры RapidFuzz над очищенными строками, разница в подготовке токенов:

- **`sort`** (`token_sort_ratio`): слова сортируются по алфавиту,
  склеиваются, дальше посимвольное сходство. Порядок слов не важен:
  `A B C == C B A`. Но **лишние слова снижают балл**: `A B C` против
  `A B C D` заметно теряет. Строгий режим, безопасен для разных песен
  одного артиста;
- **`set`** (`token_set_ratio`, дефолт): слова сравниваются как множества —
  мера берёт максимум по комбинациям «общая часть против каждой из
  сторон». Следствие: **вложение множеств даёт 100%** — `A B C` против
  `A B C D E F` идеально совпадает, лишние слова игнорируются. Агрессивный
  режим: хорош для каверов, версий и замусоренных имён, но чаще склеивает
  разное.

У посимвольной меры есть честная верхняя граница по длинам строк
$L_a, L_b$ (сходство Indel — посимвольная мера, на которой внутри RapidFuzz
построены токеновые):

$$r_{\text{text}} \;\le\; \frac{2 \min(L_a, L_b)}{L_a + L_b}$$

Почему так: Indel-сходство двух строк — это удвоенная длина их наибольшей
общей подпоследовательности, делённая на сумму длин. Подпоследовательность
не длиннее короткой строки, и максимум достигается, когда короткая строка
целиком вкладывается в длинную: тогда числитель $2\min(L_a,L_b)$, и лучше
уже не станет, как ни переставляй буквы. Если строки различаются по длине
вдвое, потолок — $2 \cdot 1/3 \approx 0.67$, и никакое «красивое»
совпадение слов его не поднимет.

На этой границе построен оптимистичный отсев (см.
[Оптимизации](#оптимизации-перебора-почему-это-быстро)): если даже
теоретический максимум не вытянет до порога, текстовое сравнение не
запускается вовсе.

### Мета-источники: четыре комбинации

Происхождение меты описано [выше](#откуда-берутся-данные): это теги
файла, которые Telegram прочитал при загрузке и отдал в атрибутах
сообщения. Здесь — о том, как она участвует в сравнении.

При `use_meta_fuzzy = True` текст считается не один раз, а во всех
комбинациях источников. У каждой записи есть два текста — очищенное имя
и очищенная мета (`performer + title` той же трубой очистки), и пары
сравниваются по всем сочетаниям:

| Код | Что с чем сравнивается | Числа для штрафа берутся из | Отметка в отчёте |
|---|---|---|---|
| NN | имя $a$ ↔ имя $b$ | числа имён обеих сторон | `(имя-имя)` |
| NM | имя $a$ ↔ мета $b$ | числа имени $a$ и меты $b$ | `(имя-мета)` |
| MN | мета $a$ ↔ имя $b$ | числа меты $a$ и имени $b$ | `(мета-имя)` |
| MM | мета $a$ ↔ мета $b$ | числа мет обеих сторон | `(мета-мета)` |

Для каждой комбинации считается свой выигрыш — текстовый вклад минус
**свой** штраф (числа берутся из тех строк, что реально сравнивались):

$$\text{выигрыш}_s = w_n \cdot r_s^{\,p_n} - \mathrm{pen}_s$$

Побеждает комбинация с максимальным выигрышем; её текстовое сходство и
становится $r_{\text{text}}$ пары. Комбинации, где мета с какой-то стороны
пуста, в конкурсе не участвуют (у них нет строки для сравнения).

Практический смысл: файл `audio_123.mp3` с мусорным именем, но нормальными
тегами сравнивается тегами и находится — например, против трека с
человеческим именем `Queen - Bohemian Rhapsody.mp3` побеждает комбинация
«мета-имя» с сходством 100%. Разобранный числовой пример — в
[примере 5](#разобранные-примеры).

## Оптимизации перебора (почему это быстро)

Сравнивать всё со всем — $O(n^2)$ — на десятках тысяч файлов больно.
Поэтому конвейер устроен каскадом фильтров, где каждый следующий шаг
дороже предыдущего, но получает всё меньше кандидатов:

1. **UID-предпроход**: одинаковые `file_unique_id` связываются до всего,
   бесплатно.
2. **Сортировка по длительности + скользящее окно.** Файлы сортируются по
   $d$; для файла $i$ кандидатами считаются только те $j$, чья длительность
   попадает в окно

   $$d_i \le d_j \le d_i + \Delta t, \qquad \Delta t = \texttt{max\_duration\_diff\_sec}$$

   Пары вне окна не рассматриваются вообще — это одновременно фильтр смысла
   («ремикс вдвое длиннее — не дубликат оригинала») и главное ускорение:
   $O(n \log n)$ на сортировку плюс сумма размеров окон вместо $n^2/2$.
   Стороны окна несимметричны неспроста: каждая пара встречается ровно один
   раз (когда в роли $i$ выступает более короткий файл), повторов нет.

   Следствие, о котором стоит знать: записи с неизвестной длительностью
   (NULL/0) сортируются в самое начало и попадают в окно только друг к
   другу и к файлам короче $\Delta t$. Файл «без длительности» против
   полноценного трека на 180 с сравниваться не будет — такую пару свяжет
   разве что одинаковый UID.
3. **Оптимистичный отсев.** Вклады длительности и размера для окна уже
   посчитаны векторно (NumPy, без Python-циклов); для `sort`-режима без
   меты верхняя граница текста берётся по формуле длин выше. Кандидат, у
   которого даже

   $$w_n \hat{r}_{\text{text}}^{\,p_n} + w_d r_{\text{dur}}^{\,p_d} + w_s r_{\text{size}}^{\,p_s} < \theta'$$

   не дотягивает до порога, отбрасывается без вызова RapidFuzz. (В
   `set`-режиме и с метой граница текста считается равной 1 — длинами
   отсекать нельзя: вложение множеств даёт 100% при любой разнице длин, а
   с метой кандидат может совпасть по мете, на которую длина имени не
   влияет.)
4. **Двухступенчатый штраф.** RapidFuzz вызывается пачкой (`cdist`) на всё
   окно выживших — все комбинации источников (имя/мета × имя/мета)
   укладываются в один матричный вызов. Затем Stage 1 отбирает пары по
   оценке **без штрафа**: штраф всегда $\ge 0$, значит оценка без него —
   честная верхняя граница, и кто не проходит её, не пройдёт и с ней.
   Только для выживших Stage 2 считает честный source-aware штраф и
   выбирает источник-победитель.
5. **Уже связанные пропускаются**: если пара уже в графе (UID или более
   раннее совпадение), повторное сравнение не делается.

Найденные пары становятся рёбрами; группы собираются обходом в ширину —
связные компоненты размера $\ge 2$, суммарно $O(n + E)$. В лог после
поиска печатается статистика: пар-кандидатов, UID- и fuzzy-связей, групп,
распределение score относительно порога (min/p25/медиана/p75/max) и
пар в секунду.

## Что происходит с группой дальше

Группа попадает в общий пайплайн (подробно — [usage.md](usage.md)).

### Верификация через API

Перед любым действием каждое сообщение группы запрашивается у Telegram
заново. Стратегия fail-safe: если хотя бы одно сообщение группы не удалось
проверить (ошибка API) — **вся группа пропускается**, лучше пропустить
дубликат, чем удалить лишнее. Дальше по результатам:

- сообщение в Telegram уже удалено → запись удаляется из локальной БД;
- сообщение больше не аудио → запись удаляется из БД;
- содержимое изменилось (не совпали UID/имя/размер/длительность/теги) →
  запись в БД обновляется;
- не изменилось → участник группы: первый проверенный в порядке
  приоритета становится оригиналом, остальные — кандидаты на удаление.

### Каскад `keep_priority`

Выбор оригинала — каскад критериев из `core.keep_priority`. Дефолт:

```ini
keep_priority = largest ~ 3%, best_meta, oldest
```

Формат: список уровней `критерий [~ допуск]`. Допуск — относительный, в
процентах от лучшего значения. Каскад работает так: на каждом уровне из
текущего набора кандидатов

1. записи, у которых значения критерия нет, выбывают (если значения нет
   ни у кого — уровень пропускается);
2. находится лучшее значение $v^*$ (максимум или минимум — по критерию);
3. выживают все в пределах допуска: $|v - v^*| \le \varepsilon \cdot |v^*|$.

Доступные критерии:

| Критерий | Лучший — это | Значение |
|---|---|---|
| `oldest` / `newest` | самое старое / новое сообщение | `message_id` |
| `largest` / `smallest` | самый большой / маленький файл | `file_size` |
| `longest` / `shortest` | самый длинный / короткий | `duration` |
| `best_meta` | самые полные теги | 0–2: +1 за валидного `performer`, +1 за валидный `title` (не плейсхолдер и не совпадающий с именем файла) |
| `longest_clean_name` | самое длинное очищенное имя | длина `clean_filename(...)` |

`oldest`/`newest` автодобавляются в конец каскада с нулевым допуском — это
гарантирует единственного победителя. Тот же каскад, повторённый на
остатке группы, даёт полный порядок fallback: если оригинал не пройдёт
верификацию (уже удалён или изменён), оригиналом станет следующий.

Пример каскада на группе из трёх (дефолт `largest ~ 3%, best_meta, oldest`):

```
Уровень largest ~ 3%:  X 8.00 МБ | Y 8.15 МБ | Z 5.00 МБ
                      лучшее 8.15, допуск ±0.24 → выживают X и Y
Уровень best_meta:     X: теги полные (2 балла) | Y: тегов нет (0)
                      допуск 0 → выживает X
[KEEP] = X; порядок fallback: X, Y, Z
```

## Разобранные примеры

Настройки — дефолты кода: $w = (0.5, 0.3, 0.2)$, $p = (1.0, 3.0, 1.0)$,
$\theta = 0.90$, $\delta = 0.08$, режим `set`.

**1. Честный дубликат.**
A: `Название_трека.mp3`, 180 с, 8.0 МБ. B: `[site.ru] название трек (1).MP3`,
182 с, 8.3 МБ. После очистки обе записи — `название трек`, числа отсутствуют
с обеих сторон.

```
r_text = 1.000                       (имена совпали полностью)
r_dur  = 180/182 = 0.989  → 0.989³ = 0.967
r_size = 8.0/8.3 = 0.964
score  = 0.5·1.000 + 0.3·0.967 + 0.2·0.964 − 0 = 0.983 ≥ 0.90  → дубликаты
```

**2. Соседние номера (за что отвечает штраф).**
`death note op 1 [nc].mp3` vs `death note op 2 [nc].mp3`, длительность и
размер совпадают, текст почти одинаков:

```
r_text = 0.96, r_dur = r_size = 1
числа: {1} ≠ {2} → pen = δ = 0.08
score  = 0.5·0.96 + 0.3·1 + 0.2·1 − 0.08 = 0.90   — ровно на пороге
```

Подними `penalty_numbers_mismatch` до 0.10 — и score падает до 0.88 < 0.90,
пара разделяется. Штраф подбирают так, чтобы типичные «соседние номера»
проваливали порог с запасом.

**3. Жаккар против бинарного (Бах).**
`...suite no 2... bwv 813... 5 menuet... 6` vs `...no 3... bwv 814...`,
$r_{\text{text}} = 0.96$, dur/size идеальны, числа
$N_a = \{2, 813, 5, 6\}$, $N_b = \{3, 814, 5, 6\}$:

```
бинарный:  pen = 0.08                      → score = 0.90 (на грани)
жаккард:   |∩| = 2 ({5,6}), |∪| = 6
           pen = 0.08·(1 − 2/6) = 0.053     → score = 0.927 > 0.90 → склеит
```

Жаккар прощает общие номера движений — но тогда и разные сюиты с одинаковым
нумерованным составом частей слипаются. Для нумерованной классики бинарный
режим надёжнее; Жаккар уместен для поп-музыки, где числа в именах — мусор.

**4. FLAC и MP3 одной песни (за что отвечает степень).**
Имя и длительность идеальны, размеры 30 МБ и 3 МБ → $r_{\text{size}} = 0.1$:

```
p_s = 1.0:  score = 0.5 + 0.3 + 0.2·0.1^1.0 = 0.82 < 0.90 → раздельно
p_s = 0.2:  score = 0.5 + 0.3 + 0.2·0.1^0.2 = 0.926 ≥ 0.90 → склеит
```

Одна и та же пара — противоположные решения из-за одной степени.

**5. Мусорное имя, нормальные теги (за что отвечает мета-fuzzy).**
A: `audio_123.mp3` (180 с, 8.0 МБ) с тегами `Queen — Bohemian Rhapsody`.
B: `03 - Queen - Bohemian Rhapsody.mp3` (182 с, 8.3 МБ) вообще без тегов.
Очистка: имя A → `audio 123`, мета A → `queen bohemian rhapsody`,
имя B → `03 queen bohemian rhapsody`, мета B — пустая.

```
NN:  «audio 123» vs «03 queen bohemian rhapsody»  → сходство мизерное
NM:  мета B пустая — комбинация выключена
MN:  «queen bohemian rhapsody» vs «03 queen bohemian rhapsody»
      → set-режим, вложение множеств → r = 1.00
MM:  мета B пустая — комбинация выключена

выигрыш MN = 0.5·1.00 − pen(числа: {} меты A vs {3} имени B) = 0.5 − 0.08 = 0.42
score = 0.42 + 0.3·0.967 (длит.) + 0.2·0.964 (размер) = 0.903 ≥ 0.90 → дубликаты
```

Пара спасена комбинацией «мета-имя»; в отчёте она так и подпишется:
`текст=1.00 (мета-имя)`. Без `use_meta_fuzzy` имена бы не совпали и пара
разлетелась.

## Как читать отчёт

В `report_duplicates.txt` у каждой группы записи отсортированы по
приоритету сохранения (первая — `[KEEP]`), после них перечислены связи с
расшифровкой:

```
--- ГРУППА #3 (Файлов: 2) ---
• [KEEP] название трек.mp3
  Track: Артист — Название
  Info: 7.63 MiB | Время: 03:00 | ID: 4973 | UID: AQADBAAD...
  Link: https://t.me/c/1234567890/4973

• [site.ru] название трек (1).MP3
  Track: не указано
  Info: 7.92 MiB | Время: 03:02 | ID: 5321 | UID: AQADCQAD...
  Link: https://t.me/c/1234567890/5321

  Связи (1):
    4973 <-> 5321: fuzzy: score=0.983 | текст=1.00 (имя-имя) | длит=0.97 | размер=0.96 | штраф=-0.00
```

- `score` — итог из формулы; сравнивается с порогом (`threshold`, с учётом
  динамического снижения);
- `текст/длит/размер` — сходство каждого критерия до умножения на вес
  (0..1), степень уже учтена;
- `(имя-имя)` … `(мета-мета)` — какая комбинация
  [источников](#мета-источники-четыре-комбинации) дала текст;
- `штраф` — вычтенный $\mathrm{pen}$;
- `идентичный файл (UID)` / `точное совпадение метаданных` — связи точного
  этапа.

При `log_level_file = DEBUG` в лог падает каждая связь ещё и в виде строки
`[MATCH] Score: ... | Text: ... (имя-мета), Dur: ..., Size: ...` — удобно
для массовой проверки, что и почему склеилось.

## Инструменты диагностики

Прежде чем крутить ручки, стоит посмотреть, что реально видит матчер:

```bash
# что стало с именами: исходное → после clean_filename → финальная форма
python main.py export cleaned-names [ЧАТ]      # без аргумента — вся БД

# то же для тегов: performer, title → после clean_meta → финальная форма
python main.py export cleaned-meta [ЧАТ]

# найти похожие на «...» по всей БД: топ-20, схожесть ≥ 70%
python main.py search "bohemian rhapsody"
python main.py search "bohemian" --min-score 50   # порог 0..100
python main.py search "bohem" --wratio            # короткие обрывки с опечатками
```

`search` всегда использует `token_set_ratio` независимо от `matching_mode`
конфига — это настройка строгости дедупликации, а поиску нужна полнота.
`--wratio` переключает на WRatio: ловит короткие обрывки с опечатками, но
шкала у него сжатая (слово найдено ≈ 90).

Если матчер что-то не то склеивает — начинать с `cleaned-names`/`cleaned-meta`:
чаще всего выясняется, что очистка съела различимую часть имён (или,
наоборот, оставила мусор, который и слипся).

## Тюнинг: симптом → ручка

| Симптом | Что крутить |
|---|---|
| Дубликаты не находятся | `threshold` ↓ до 0.85; `matching_mode = set`; проверить `cleaned-names` — может, очистка съедает различимую часть имён; `max_duration_diff_sec` ↑, если одно и то же лежит с разной обрезкой |
| Склеивается разное (разные треки одного артиста) | `name_power` ↑ (1.3–1.6); `use_jaccard_penalty = False` и `penalty_numbers_mismatch` ↑; `matching_mode = sort`; `threshold` ↑ |
| Каверы/версии считаются дублями, а не надо | `duration_power` ↑ (строже к длительности) и/или `max_duration_diff_sec` ↓ |
| FLAC и MP3 одной песни не склеиваются (а надо) | `size_power` ↓ до 0.2–0.5 — размер зависит от битрейта и обложек |
| Файл с мусорным именем не находится | Проверить теги в `cleaned-meta`: `use_meta_fuzzy = True` должен быть включён (дефолт) |
| Пары с нулевой длительностью разлетаются | Двое «без длительности» сравниваются с пониженным порогом — но файл без длительности не сравнивается с длинным треком (окно, см. [Оптимизации](#оптимизации-перебора-почему-это-быстро)): такую пару свяжет только одинаковый UID. Перед удалением всё равно обязательна верификация по API |
| Медленно | Обычно окно уже узкое; можно сузить `max_duration_diff_sec`, поднять `db_cache_size`, проверить, не включён ли `use_meta_fuzzy` зря (мета расширяет набор комбинаций) |

Тюнинг вслепую не работает: сначала `python main.py report` +
`export cleaned-names`, потом одна ручка за прогон.
