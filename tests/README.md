# Тестовый набор dedup

243 теста, полный прогон ~1.5 секунды. Конфигурация pytest живёт в `pyproject.toml`
(`testpaths`, режим asyncio, маркеры), поэтому запускать нужно **из корня проекта**.

## Запуск

```bash
# Из корня проекта
source .venv/bin/activate
pytest

# или без активации окружения
.venv/bin/python -m pytest tests/
```

Полезные варианты:

```bash
pytest -v                                # каждый тест построчно
pytest -x                                # стоп на первом падении
pytest --tb=short                        # короткие трейсбеки
pytest --durations=10                    # 10 самых медленных тестов

pytest tests/test_priority.py            # один файл
pytest tests/test_priority.py::test_largest   # один тест
pytest -k "tolerance or cascade"          # по ключевому слову в имени

ruff check .                              # линт (проекта и тестов)
```

## Тесты с живой БД (маркер `livedb`)

Интеграционные тесты работают с **копией** живой базы `music_library.sqlite`:

- копия создаётся во временном каталоге один раз на сессию прогонов;
- оригинальная БД открывается только на чтение (при копировании) и никогда не изменяется;
- если `music_library.sqlite` отсутствует (другая машина, чистый чекаут) —
  эти тесты автоматически пропускаются, остальной набор работает как обычно.

```bash
pytest -m livedb             # только тесты на живой БД (8 шт)
pytest -m "not livedb"       # всё кроме них (235 шт)
```

Что проверяют livedb-тесты:

- точная группировка дубликатов по всем чатам совпадает с независимым
  SQL-оракулом (union-find против BFS прод-кода);
- экспорты (txt/csv) и отчёт о дубликатах дают ровно те количества строк,
  которые насчитывает SQL;
- `validate_database` проходит на реальных данных.

## Golden-числа fuzzy-матчера и REGEN_GOLDEN

`golden/fuzzy_group_counts.json` фиксирует число групп и рёбер fuzzy-группировки
для каждого чата живой БД при текущих настройках фабрики тестов. Файл привязан
к настройкам хэшем (`settings` в json): поменялись дефолты фабрики — тест
сам об этом скажет.

**Когда перегенерировать:** после осознанного изменения логики матчера
(`dedup/fuzzy.py`) или дефолтов секции `fuzzy` в фабрике `make_settings`
(`tests/conftest.py`), когда новое поведение проверено и признано правильным.

**Как:**

```bash
REGEN_GOLDEN=1 pytest tests/test_livedb_fuzzy.py   # записать новые числа
pytest tests/test_livedb_fuzzy.py                  # проверить сравнение
```

После изменения живой БД (синхронизировали новые чаты) в golden могут
появиться отсутствующие чаты — это тоже лечится перегенерацией.

## Устройство набора

| Файл | Роль |
|---|---|
| `conftest.py` | Фабрика `make_settings()` (полный `Settings` с оверрайдами по секциям), фикстуры БД, автосброс глобалов `state.py` |
| `fakes.py` | `FakeClient` — программируемый клиент Telegram без сети; конструкторы сообщений/чатов |
| `helpers.py` | Построители строк-данных, независимый SQL-оракул группировки, чтение БД только-для-чтения |
| `golden/` | Эталонные числа fuzzy-матчера (см. выше) |
| `test_livedb_*.py` | Интеграция с копией живой БД (маркер `livedb`) |
| остальные `test_*.py` | Юнит-тесты и тесты слоя БД на синтетике; сеть не используется нигде |

Инварианты безопасности (нарушать нельзя):

- все пути из настроек (БД, экспорты, бэкапы, downloads, lock) указывают в
  `tmp_path` — реальные файлы проекта не затрагиваются;
- `session_name` указывает на несуществующий файл — файл сессии
  `my_account.session` не читается;
- ни один тест не выходит в сеть: вместо клиента Telegram — `FakeClient`.
